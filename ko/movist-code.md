# movist-code 한국어 번역

설치되는 스킬은 영어 원문 `skills/movist-code/SKILL.md`이다. 이 파일은 내용을 확인하려고 둔 번역이며 원문과 같은 커밋에서 함께 고친다.

**설명(description)**: Movist의 기능 구현, 확인된 버그 수정, 리팩토링에 사용한다. 요청한 것만 가장 단순한 흐름으로 구현하고, 기존 구현의 재사용과 재생 중 CPU 비용을 우선한다. 변경 리뷰에는 movist-review를 사용한다. 원인 조사·성능 측정만 하는 요청에는 사용하지 않는다.

# Movist 코드 구현·리팩토링

요청한 동작을 빠짐없이 완성하되 새 코드는 가장 적게 쓴다. 작업 저장소의 지침 파일(`AGENTS.md`, `CLAUDE.md` 등)과 사용자가 지정한 변경·검증 범위를 따른다.

## 용어

- 사용자: 일을 맡긴 사람.
- end user: 앱을 쓰는 사람.
- 재생 hot path: 미디어를 재생하는 동안 초당 수십~수백 회 실행되는 코드.
- 단순한 코드 흐름: 분기, 상태, 호출 계층, 스레드·actor 이동이 적은 것.

## 범위

- 요청한 것만 구현한다. 요청에 없는 기능, 옵션, 일반화, 방어 코드, 리팩토링이 필요해 보이면 넣기 전에 무엇을 왜 넣으려는지 말하고 승인받는다.
- 변경이 닿아야 하는 호출부, 테스트, fixture, 문서는 요청의 일부다. 빠뜨리지 않는다.
- 끝내기 전에 요청 밖의 자신의 수정을 되돌린다. 결국 필요했던 것은 이유와 함께 보고한다. 자신이 만들지 않은 변경은 건드리지 않는다.
- 요청이 요구하지 않았는데 여러 타입의 actor 격리, public 계약, 저장 형식처럼 blast radius가 넓은 변경이 필요해지면 고치기 전에 알리고 승인받는다.
- 설계만 요청받았으면 구현하지 않는다. 멈추라고 하면 바로 멈춘다.
- root cause가 확인되지 않은 증상을 짐작으로 고치지 않는다. 증상을 없애는 코드를 더하기 전에 전체 흐름에서 root cause를 찾아 그 자리에서 고친다.

## 가장 작은 완전한 변경

아래 순서에서 처음으로 되는 것을 고른다.

1. 없어도 되는가. 옵션, 분기, 기능을 없애면 흐름이 단순해지는지 먼저 본다. 없애도 될 것 같으면 사용자에게 묻는다.
2. 이미 있는가. 영향을 받는 호출 경로와 데이터·상태를 맡은(owns) 타입을 확인하고, 같은 일을 하는 기존 함수, 타입, 상수, 기본값, fallback을 쓴다. 비슷한 것을 새로 만들지 않고 필요한 기능은 그것을 맡은 module에 더한다.
3. 표준 라이브러리나 플랫폼 API가 하는가. 그것을 쓴다. 이 코드에 필요 없는 기능 때문에 범용 component를 들이지 않는다.
4. 그래도 필요하면 동작하는 최소한을 쓴다.

- 추상화, 방어용 검사, 호환 코드, retry, cache, rollback은 현재 요구나 실제 실행 조건, 유지해야 할 계약으로 필요성을 설명할 수 있을 때만 넣는다. 실제 중복을 줄이고 책임을 분명히 하는 공통화는 사용한다.
- 거의 일어나지 않거나 end user가 다시 시도하면 되는 실패를 막는 코드를 넣지 않는다. 복구를 시도하지 않고 실패를 드러낸 뒤 return한다. end user가 시작한 동작이면 알림으로, 그 밖에는 로그로 드러낸다. 자원 해제처럼 실패 경로에서도 지켜야 하는 것은 지킨다.
- 추측한(speculative) 사용처나 제품이 대상으로 하지 않는 플랫폼을 위한 타입, protocol, 인자, 간접 계층은 넣지 않는다. 계획된 기능이 쓸 것은 남긴다.
- 출시된 적 없는 저장 형식과 저장소 안에서만 쓰는 API에는 version, migration, 호환 코드를 넣지 않는다. 없어도 되는 새 직렬화 필드는 Optional이나 decoding 기본값으로 둔다.
- macOS와 iOS가 같은 개념으로 처리할 수 있으면 공용 코드로 만든다. 한 플랫폼에만 있는 special case는 단순한 fallback으로 둔다.
- Movist 2(저장소의 `__original/`에 있는 출시된 앱)와 같은 동작을 요청받았다면 거기에서 해당 기능의 설정, 동작 순서와 상태 전이를 확인한다. 동작은 빠뜨리거나 넓히지 않고 따르되, 구현은 현재 코드에서 가장 단순한 방법을 찾는다.
- 변경 뒤 제품 코드가 늘었으면 늘어난 코드가 모두 필요한지 다시 본다. 단순화가 목적인 변경에서 코드가 늘었으면 그 이유를 보고한다.

## CPU 비용과 흐름 단순화

- 재생 hot path의 우선순위는 실제 앱의 CPU 부하 감소 → 코드 흐름 단순화 → 코드량 감소 → 검수 편의다. 기능의 정확성과 수명·동시성 invariant를 유지하면서 이 순서로 판단한다. 줄 수를 줄이려고 재생 hot path의 복사, 할당, 스레드·actor 이동, 동기화, callback 안에서 하는 일을 늘리거나 무관한 책임을 한 객체에 모으거나 세미콜론으로 여러 문장을 한 줄에 넣거나 풀어 읽어야 하는 축약 코드를 쓰지 않는다.
- CPU 최적화의 가치는 호출 빈도와 호출당 비용이 실제 앱의 CPU 부하에 미치는 영향으로 판단한다. 재생 hot path처럼 누적 비용이 큰 경로를 우선한다. 새 API나 라이브러리 경로가 더 효율적이라고 가정하지 않는다.
- 한 번 드는 비용을 아끼거나 실제 앱에서 매우 미미한 성능 개선을 위해 코드 흐름을 복잡하게 하거나 책임의 경계와 객체 수명의 경계를 흐리지 않는다. 컴파일러가 최적화할 수 있는 함수 inline이나 계산 축약을 직접 하거나, 분리돼야 할 함수 계층을 한 함수로 합치는 것이 그 예다. seek·영상 시작·종료 시 객체 초기화 비용은 한 번 드는 비용의 예시다.
- 중복 기본값, 다른 상태에서 계산할 수 있는데 따로 저장한 상태, 서로 맞춰 둬야 하는 boolean, 전달만 하는 wrapper, 이미 가진 객체에서 계산할 수 있는 인자 전달과 불필요한 호출 계층을 줄인다.
- 숨긴 UI나 꺼진 기능의 불필요한 반복 작업을 줄일 때는 다시 켜졌을 때 필요한 상태와 동작을 유지한다. 구독 해제·재연결이나 별도 상태 기계를 먼저 추가하지 말고 기존 흐름에서 해결할 수 있는지 확인한다.

## 이름·책임·제거 범위

- 함수·인자·타입 이름에 실제 동작과 조건이 드러나게 한다. 상태 변경 책임과 callback을 호출해야 하는 조건을 명확히 하고 관련 구현을 그 책임을 가진 위치에 둔다.
- document나 app delegate처럼 이미 많은 action과 callback을 받는 타입에 편하다는 이유로 구현을 더하지 않는다. 그 일을 맡은 타입에 두거나, 없으면 어디에 둘지 묻는다.
- 값의 종류는 문자열이 아니라 타입으로 나타낸다. 뜻이 다른 값을 `.other` 같은 한 case로 합치지 않는다.
- 조정 값을 쓰는 자리에 hard-code하지 않고 이름을 붙여 한 번 정의한다. 설정 기본값은 한 곳에서 등록한다.
- 효과를 설명할 수 없는 키워드나 언어 구문을 넣지 않는다. `nonisolated`, `withExtendedLifetime`처럼 없을 때 무엇이 잘못되는지 말할 수 없는 것이 그 예다.
- 동작을 제거하라는 요청이면 같은 동작을 다른 계층으로 옮겨 남기지 않는다. 끄거나 떼어 내기만 하라는 요청이면 다시 쓰는 데 필요한 구현까지 삭제하지 않는다.
- 요청 범위 안의 미사용 API만 외부 사용 여부와 유지해야 할 계약을 확인한 뒤 정리한다. 주변 미사용 API까지 변경 범위를 넓히지 않는다. `public`이나 `package`라는 이유만으로 호환 코드를 남기거나, 현재 호출부가 없다는 이유만으로 삭제하지 않는다.
- 저장소가 생성하는 산출물은 저장소가 추적하는 생성 도구와 입력을 고쳐 바로잡아, 다시 생성해도 유지되게 한다.

## 로그·진단·테스트 전용 코드

- 로그는 문제가 생겼을 때 원인을 확인할 정보만 남긴다. 로그를 위한 timer, 누적 통계, 재생 hot path에서 호출마다 하는 활성 여부 검사를 넣지 않는다.
- 제품에 남는 로그·진단 코드는 `<Type>+Debug.swift`라는 이름의 extension 파일로 분리해 제품 코드를 가리지 않게 한다.
- 임시 계측 코드와 실험용 변경은 조사가 끝나면 지운다. 실험할 때는 제품 코드를 지우지 말고 잠시 막는다.
- 테스트에서만 쓰는 코드는 테스트 target에 둔다.

## 기술 설명과 변경 요약

- 주석, 설계 설명, 작업 보고에서 특정 타입·함수·프로퍼티를 가리킬 때는 실제 식별자를 그대로 쓴다. `PlaybackSession`을 “재생 세션”으로 바꾸는 등 대상을 다시 추측해야 하는 번역이나 일반화는 피한다.
- `IPC`, `actor`, `callback`처럼 익숙한 기술 용어는 그대로 쓴다. 한국어로 억지 번역해 의미를 흐리지 않는다.
- 작업 중에 붙인 별칭으로 대상을 가리키지 않는다. 어떤 파일이나 입력에서, 코드가 무엇을 하고, end user에게 무엇이 보이는지를 쓴다.
- 변경 요약은 대상과 실제 변경을 직접 쓴다. 예를 들어 “재생 세션 소유권 주석 정리” 대신 “PlaybackSession 주석 정리”라고 쓴다. 객체의 수명이나 책임의 경계 자체를 설명할 때는 누가 무엇을 생성·보관·해제하거나 변경하는지 구체적으로 적는다.
- 커밋은 사용자가 지시할 때만 한다. 커밋을 요청받으면 [movist-commit](../skills/movist-commit/SKILL.md)을, 리뷰를 요청받으면 [movist-review](movist-review.md)를 읽고 따른다.

## 문서 갱신

- 저장소에 여기에 적은 문서들이 있을 때 적용한다. 코드 변경이 public·package 계약, caller에게 보이는 동작이나 wire 계약을 바꾸면 그 owner 문서(`Docs/3.0`의 해당 `*API.md`·`*Spec.md`)를 그 문서의 수준으로 고치고 다른 문서는 건드리지 않는다. 상태나 완료 조건이 바뀌면 `Docs/3.0/Migration-Plan.md`의 해당 영역 행을 함께 고친다. 구현하는 기능에 Migration Plan이 링크한 `Docs/Working` 작업 문서가 있으면 그 문서의 관련 절을 먼저 읽고, 단계 코드가 들어가는 커밋에서 구현된 계약은 API 문서로, 결정은 Design 문서로 옮긴 뒤 작업 문서에서 그 부분과 끝난 단계를 지운다. 검증 결과는 작업 보고에만 쓰고, 남는 결함·한계는 `Docs/Issues`에 `처리` 값과 함께 적는다. Issues 항목을 고쳤으면 같은 커밋에서 그 항목을 `해결된 항목` 표로 옮기고 커밋 hash는 적지 않는다.

## 주석

- 코드에서 드러나는 동작을 되풀이하는 주석은 추가하지 않는다. lock, cancellation, 객체 수명, 외부·플랫폼 동작, API 계약, 호환성처럼 코드만으로 알기 어려운 제약과 이유는 보존하거나 설명한다. 저작권 헤더, shebang, formatter/linter 지시문은 원래 형식을 따른다.
- 한국어로 쓴다. 영어가 명백히 더 명확하면 새 주석도 영어로 쓰고 기존 영어 주석도 유지한다. 한 문장은 한 줄에 쓰고 여러 `///` 줄로 나누지 않는다.
- 타입 주석은 관리 대상과 역할부터 설명한다. `identity`, `generation`, “보호 상태”만 나열하지 않는다.
- 동작 주석은 실제 함수·상태에 연결해 조건, 순서, 이유를 설명한다. 기술적 정확성을 유지하고 불분명한 직역은 피한다.

## 변경에 맞는 검증

- 변경한 동작과 영향받는 플랫폼에 필요한 검증을 선택한다. 사용자가 코드 수정만 요청하거나 앱 검증을 맡겠다고 한 경우에는 그 경계를 지킨다. 완료한 검증은 입력이 바뀌거나 새로운 우려가 생겼을 때만 반복한다.
- 테스트는 바뀐 코드를 실행하는 메서드만 돌린다. 바뀌지 않은 영역을 다시 테스트하지 않는다.
- 직접 확인할 수 있는 동작은 사용자에게 넘기지 않고 확인한다. 실행 중인 앱은 저장소가 제공하는 IPC나 명령행으로 확인하고, 사용자의 화면과 키보드를 차지하는 조작은 피한다.
- 빌드·테스트의 성공과 화면·소리·기기에서 확인한 것을 구분해 보고한다. 확인하지 않은 것은 미검증으로 적는다.
- 설계를 따져 보면 정해지고 측정이 보탤 것이 없는 문제에 측정을 요구하지 않는다. 매 변경마다 전체 빌드·서명·기기 검증·CPU 측정을 의무화하지 않는다. Release 앱 CPU를 반복 측정·비교할 때는 사용할 수 있는 `movist-cpu-benchmark` 스킬의 절차를 따른다. 측정하지 않은 비용 개선은 추정으로 구분한다.
