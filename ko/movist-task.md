# movist-task 한국어 번역

설치되는 스킬은 영어 원문 `skills/movist-task/SKILL.md`이다. 이 파일은 내용을 확인하려고 둔 번역이며 원문과 같은 커밋에서 함께 고친다.

**설명(description)**: Movist 작업 보드에서 작업 하나를 가져와 시작할 때 사용한다. 로컬 main 위로 rebase하고, 사용자의 보드 사람으로 작업을 claim하고, 명세와 source를 읽고, 진행 중인 작업과 겹치는지 확인한 뒤, 확정받을 설계를 보고한다. 코드나 문서를 고치기 전에 멈춘다. 사용자가 작업 번호를 주거나 주지 않고 보드 작업을 가져오라, 집으라, 시작하라고 할 때 쓴다("할일 가져와", "보드에서 다음 일", "M1-4 시작"). 보드를 만들거나 바꾸는 일, 구현·리뷰·병합에는 쓰지 않는다.

# Movist 보드 작업 시작

작업 보드에서 작업 하나를 가져와 사용자가 확정할 수 있는 설계까지 만든다. 사용자는 일을 맡긴 사람이고, end user는 앱을 쓰는 사람이다.

보드를 읽고 쓰는 방법은 저장소의 보드 규칙 파일에 있고, 그 파일은 `AGENTS.md`의 `Task board` 블록이 가리킨다. 보드를 읽고 쓸 때는 항상 그 파일과 보드의 `meta/rules`를 따른다. 이 스킬은 그 둘이 정하지 않은 것만 정한다. 누구로 claim하는지, 어느 작업을 가져오는지, 설계 전에 무엇을 하는지, 어디서 멈추는지다.

## 선

1. 지시에 적힌 보드 사람으로만 claim한다. 사람을 추측하지 않는다.
2. 보드에 쓰는 모든 시각은 그 쓰기 직전에 실행한 `date -u +%Y-%m-%dT%H:%M:%SZ`에서 얻는다. 시각을 어림하거나 앞서 얻은 시각을 다시 쓰지 않는다.
3. 사용자가 설계를 확정하기 전에는 코드도 문서도 고치지 않는다. 이 스킬이 바꾸는 것은 rebase와 아래에 적힌 보드 쓰기, 세션 title뿐이다.

## 순서

1. 현재 branch를 `git rebase main`으로 로컬 `main` 위로 rebase한다. 보드를 읽기 전에 매번 한다. 미커밋 변경 때문에 git이 거절하거나 rebase가 충돌하면, 진행 중인 rebase가 있을 때 `git rebase --abort`를 실행하고, 관련된 파일을 보고한 뒤 보드를 건드리지 않고 멈춘다. 사용자 없이 stash하거나 버리거나 충돌을 해결하지 않는다.
2. 자기 보드 사람을 찾는다. 지시에 `Task board id: <id>` 형식의 줄로 적혀 있다. 그런 줄이 context에 없으면 누구로 claim할지 사용자에게 묻는다. git 사용자, 계정, 이메일 주소, 다른 작업의 owner에서 추론하지 않는다. 그 id가 `meta/config`의 `people`에 있는지 확인하고, 없으면 묻는다.
3. 보드 규칙이 작업 시작 때 읽으라고 한 대로 보드를 읽는다. 이어서 ready 작업(`waitingOn`이 빈 `todo`)과 `doing`, `review`, `blocked`인 작업을 query한다.
4. 작업을 고른다.
   - 사용자가 key를 줬으면 그 작업을 가져온다. 그 작업이 `todo`가 아니거나, 아직 다른 작업을 기다리거나, 다른 사람이 owner이면 claim하지 않고 상태를 보고한 뒤 멈춘다.
   - 사용자가 key를 주지 않았으면, ready 작업에서 `meta/rules`가 가져오면 안 된다고 한 것과 다른 사람이 owner인 것을 빼고, key 번호가 가장 작은 것을 가져온다. 나머지 ready 작업은 보고에 한 줄씩 적는다.
   - 가져올 수 있는 작업이 없으면, 어느 작업이 진행 중인지와 기다리는 작업이 각각 무엇을 기다리는지 보고하고 멈춘다.
5. `details/<key>`를 읽고, 보드 규칙대로 한 번의 batch로 작업을 claim한다. `claimedBy.session`에 worktree 이름을, `branch`에 현재 branch를 적는다. claim 메시지에는 어느 branch에서 일하는지와 무엇을 먼저 읽을지를 적는다. 다른 사람이 먼저 가져가 claim이 실패하면 4번으로 돌아간다. claim이 성공하면, 현재 세션의 이름을 바꾸는 도구가 있을 때(예: `session_id`를 `self`로 주는 `set_session_title`) 세션 title을 작업 key와 보드 제목(`<key> <title>`)으로 바꾼다. 그런 도구가 없으면 건너뛴다.
6. 작업에 필요한 것을 읽는다. `details`의 `spec` 위치에서 시작해, `AGENTS.md`가 그 영역의 작업 전에 읽으라고 한 문서를 읽고, source를 추적한다. 작업이 고칠 타입과 함수, 그 호출자, 관련 테스트다. 문서가 지금 동작을 설명하면 source에서 확인하고, 어긋나는 것을 모두 보고한다.
7. 겹침을 확인한다. 다른 세션이 잡은 `doing`·`review` 작업마다, 이 작업이 고칠 파일을 그 작업의 `branch`에서 바뀐 파일(`git diff --name-only main...<branch>`)과 비교하고, 그 작업의 worktree가 이 기기에 있으면 미커밋 변경과도 비교한다. 겹치면 보고하기 전에 그 작업의 thread에 파일 이름을 적은 `note`를 올린다.
8. [movist-code](movist-code.md)의 규칙으로 변경을 설계한다. 작업이 요구한 것만 만들고, 이미 있는 것을 쓰고, 최소 수정보다 가장 단순한 결과를 먼저 고르고, blast radius가 넓은 변경은 따로 밝힌다. 구현하지 않는다.
9. 제안을 작업의 thread에 세 줄 이내로 올린다. 사용자가 정할 것이 있으면 type을 `question`으로, 없으면 `update`로 한다. 그런 다음 보고하고 멈춘다.

## 보고

보고는 한국어로 쓴다. 타입, 함수, property는 실제 식별자로 가리킨다. 적을 것이 없는 부분은 뺀다. 작은 작업은 부분마다 한 줄이다.

- 첫 줄: 작업 key와 제목, 그리고 일의 종류(`코드 변경`, `문서만`, `결정만`). 고칠 코드가 있는지 사용자가 알 수 있게 종류를 가장 먼저 밝힌다.
- `작업 위치:` worktree 경로, branch, rebase가 한 일(어느 커밋에서 어느 커밋으로, 또는 이미 최신).
- `지금 동작:` source가 보여 주는 것을 `file:line`과 함께. 문서와 source가 어긋나는 곳도 적는다.
- `제안:` 설계. 결정마다 end user에게 무엇이 달라지는지 적는다. 설계가 최소 수정보다 눈에 띄게 많이 다시 쓰면, 최소 수정이 무엇이었고 이 설계가 무엇을 단순하게 하는지 한 줄로 적는다.
- `고칠 곳:` 고칠 타입, 파일, 문서. public·package 계약, 저장 형식, actor 격리의 변경은 표시한다.
- `겹치는 작업:` 작업 key, 잡은 사람, 겹치는 파일. 선택지를 준다. thread에서 조율하며 계속하거나, 이 작업을 놓고 다음 작업을 가져오는 것이다.
- `정하실 것:` 사용자만 정할 수 있는 것. 각각에 권하는 답을 붙인다.
- `확인 못 한 것:` 한 줄씩.
- `이 작업 뒤:` `deps`에 이 작업이 있는 작업들과 각각이 그 밖에 무엇을 더 기다리는지. 사용자가 key를 주지 않았으면 나머지 ready 작업도 적는다.

## 보고한 뒤

- 사용자가 설계를 확정하거나 바꾸면, 확정된 설계를 고칠 파일과 함께 thread에 `update`로 올린다. 작업의 일이 결정 자체이면, 확정된 답을 `acceptance`가 말한 곳에 적는다.
- 구현은 사용자가 시킬 때만 movist-code를 따라 한다. 리뷰를 요청받으면 [movist-review](movist-review.md)를 따른다. 커밋과 병합은 사용자가 시킬 때만 [movist-commit](../skills/movist-commit/SKILL.md)과 [movist-ff-main](../skills/movist-ff-main/SKILL.md)으로 한다.
- 그 뒤의 작업 상태는 보드 규칙과 `meta/rules`대로 바꾼다.
- 사용자가 작업을 놓기로 하면, 보드 규칙이 끝내지 못한 작업에 대해 말한 대로 두고 4번부터 다시 시작한다.
